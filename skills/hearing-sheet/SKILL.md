# ヒアリングシート記入スキル

Google Drive 上の案件フォルダにあるヒアリングシート（雛形）をもとにユーザーへヒアリングを行い、
回答を「記入済みシート」として Drive に保存し、ローカルの `docs/idea.md` にも書き出す。

## 前提: Google Drive MCP の制約

このワークフローは Google Drive コネクタ（MCP）を使う。ツールが deferred の場合は
ToolSearch で「drive search read create file」等を検索してロードすること。

**重要な制約**: この Drive コネクタは読み取り（`search_files` / `read_file_content` /
`get_file_metadata`）と新規作成（`create_file`）・コピー（`copy_file`）のみ対応。
**既存ファイルの更新・削除はできない**（Google Drive for Desktop のローカルマウントも
この環境には無いため、Bash 経由の削除も不可）。

一方で、記入済みシートは後段の**案件管理システムが読み込む**ため、
**元のヒアリングシートと同じファイル名でなければならない**（「_記入済み」等の接尾辞は付けない）。

この 2 つの事情から、保存は次の方式で行う:

1. 記入済み内容を**元のシートと同じタイトル**の新規 Google ドキュメントとして同じフォルダに作成する
2. 作成・内容確認が完了した後、**旧雛形ファイルの削除をユーザーに依頼する**（リンクを提示して 1 クリックで済むようにする）

削除依頼を省略しないこと。同名ファイルが 2 つ残ると、案件管理システムが旧雛形の方を
読み込んでしまう恐れがある。

## フォルダ構造の前提

```
<案件フォルダ>/            ← 案件ごとの親フォルダ
└── 00_案件概要/
    └── ヒアリングシート    ← Google ドキュメント。ヒアリング項目の雛形
```

## ステップ 1: 案件フォルダの特定

1. ユーザーの発話に案件名が含まれていなければ、まず案件名を尋ねる。
2. `search_files` でフォルダを検索する:
   `title contains '<案件名>' and mimeType = 'application/vnd.google-apps.folder'`
3. 候補が複数ある場合、まず各候補の直下に「00_案件概要」があるかを `parentId` 検索で
   確認する。1つだけが該当するならそれが案件フォルダである（親コンテナと案件フォルダが
   入れ子でヒットするケースが多いため）。それでも曖昧なら AskUserQuestion で選択してもらう。
   確定後はフォルダ名を提示して認識合わせをしてから進む（似た名前の案件を取り違えると、
   以降のヒアリング全体が無駄になるため）。
4. 見つからない場合は部分一致のキーワードを変えて再検索し、それでもだめなら
   ユーザーにフォルダ名の正確な表記か URL を聞く。

## ステップ 2: ヒアリングシートの発見

1. 案件フォルダ直下から `parentId = '<案件フォルダID>' and title contains '00_案件概要'` で概要フォルダを探す。
2. その中から `parentId = '<00_案件概要ID>' and title contains 'ヒアリングシート'` でシートを探す。
3. 記入済みシートは雛形と同名なので、ファイル名では区別できない。`read_file_content` で
   内容を読み、**回答が既に記入されているか（雛形のままか）**で判断する。記入済みだった場合は
   過去にヒアリング済みの案件なので、「再ヒアリング（前回回答を引き継いで更新）」か
   「最初からやり直し」かをユーザーに確認する。
4. 同名のシートが複数見つかった場合は、前回実行時に旧雛形の削除が漏れている可能性が高い。
   各ファイルの内容と `modifiedTime` を確認して雛形／記入済みを特定し、状況をユーザーに
   報告して不要な方の削除を案内してから進む。
5. 見つからない場合はフォルダ内のファイル一覧（`parentId` 検索の結果）を提示し、
   どれが該当するかユーザーに指定してもらう。命名が揺れているケース
   （「ヒヤリングシート」「hearing sheet」等）も考慮して検索する。

## ステップ 3: 雛形の読み込み

`read_file_content` で雛形を読み、ヒアリング項目を抽出する。

- 雛形の項目・順序・構造はそのまま尊重する。勝手に項目を追加・削除・改名しない
  （雛形は組織の標準であり、成果物の一貫性が重要なため）。
- 項目に補足説明や記入例が書かれていれば、質問時のガイドとして活用する。
- 雛形が大規模（目安: 質問が50問以上）な場合や、「最小ヒアリング版」「簡易版」のような
  縮約セクションが用意されている場合は、いきなり始めずに AskUserQuestion で
  進め方（フル / 最小版 / 特定セクションのみ）を選んでもらう。ユーザーの時間は有限であり、
  全問を強制すると途中離脱や雑な回答を招くため。

## ステップ 4: ヒアリングの実施

- **関連する 2〜3 項目をまとめて 1 回の質問として提示**し、通常のチャットで回答してもらう。
  一問一答はテンポが悪く、全項目一括は回答漏れが出やすい。項目のグルーピングは
  意味的な近さ（例: 背景と目的、予算と納期）で判断する。
- 回答が曖昧・不足している場合は軽く深掘りする。ただし尋問にならないよう、
  1 項目につき深掘りは 1 回程度に留める。
- ユーザーが「スキップ」「わからない」「後で」と言った項目は「（未記入）」として残す。
- 全項目が終わったら、**項目と回答の一覧をサマリとして提示し、修正がないか確認**してから
  保存に進む。保存後の修正は Drive 側でファイルを作り直すことになりコストが高い。

## ステップ 5: 保存

確認が取れたら、以下の 2 箇所に保存する。

### 5-1. Google Drive（記入済みシート）

`create_file` で新規 Google ドキュメントを作成する:

- `parentId`: 「00_案件概要」フォルダの ID
- `title`: **元のシートとまったく同じタイトル**（接尾辞・日付などは一切付けない。
  案件管理システムがこのファイル名で読み込むため）
- `textContent`: 雛形と同じ構成の Markdown（見出し・項目名は雛形に合わせる）
- `contentMimeType`: `text/markdown`（Google ドキュメントに自動変換される）

Markdown 生成時の注意（Docs 変換の既知の癖）:

- **表のセル内では `**太字**` などの強調記法を使わない**。変換時にエスケープされ
  `\*\*` が本文に残ってしまう。表ヘッダーは素のテキストにする。
- 作成後のレスポンスで `fileSize` が `1` でも異常ではない（Google ネイティブ文書の仕様）。
  内容確認は `read_file_content` で読み戻して行う。変換が崩れていた場合のみ
  `text/html` で作り直す。

**新しいシートの作成と内容確認（読み戻し）が完了してから**、旧シート
（初回は雛形、再ヒアリング時は前回の記入済みシート）の `viewUrl` を提示し、
その場で手動削除してもらうよう依頼する。順序が重要:
先に削除を依頼すると、作成に失敗した場合にシートが失われるため、
必ず「新シートの作成成功 → 旧シートの削除依頼」の順で行う。

### 5-2. ローカル `docs/idea.md`

現在のプロジェクトの `docs/idea.md` に以下の形式で書き出す（`docs/` がなければ作成）:

```markdown
# <案件名> ヒアリング内容

- 案件フォルダ: <Drive 上のフォルダ名>
- 記入日: <YYYY-MM-DD>
- 記入済みシート: <作成した Google ドキュメントの URL>

## <項目1>
<回答>

## <項目2>
<回答>
...
```

既に `docs/idea.md` が存在する場合は、上書きしてよいか確認してから書き込む。

## 完了報告

最後に以下を簡潔に報告する:

- 作成した Google ドキュメントのタイトルとリンク
- **旧シートの削除依頼**（旧シートのリンクを再掲。ユーザーが削除済みと言うまでリマインドを残す）
- `docs/idea.md` のパス
- 未記入のまま残した項目があればその一覧（後で埋める TODO として）
