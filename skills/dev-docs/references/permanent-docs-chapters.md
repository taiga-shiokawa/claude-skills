# 永続的ドキュメント（`docs/`）の定義

`/dev-docs` の参照資料。各ファイルの所有範囲・更新条件・章立てを定義する。
`doc-writer` サブエージェントは各ファイルの執筆時にこの定義を適用する。

アプリケーション全体の「**何を作るか**」「**どう作るか**」を定義する恒久的なドキュメント。
アプリケーションの基本設計や方針が変わらない限り更新されない。

## 所有範囲と更新条件

同じ情報は所有文書に1回だけ書き、他文書から参照する。

| 文書 | 所有する情報 | 読む・更新する条件 |
|---|---|---|
| `product-requirements.md` | ビジョン、対象ユーザー、課題、製品スコープ、機能・非機能要求、成功条件 | ユーザー価値、提供範囲、受け入れ条件が変わる |
| `functional-design.md` | 安定したユースケース、振る舞い、画面遷移、外部契約、データモデル | API、データ、主要フロー、ユーザー向け挙動が変わる |
| `architecture.md` | 技術選択、実行・配備構成、モジュール境界、依存方向、横断的制約 | 技術、境界、依存、性能・セキュリティ方針が変わる |
| `repository-structure.md` | 安定したディレクトリ責務、配置規則、公開境界 | 新しい配置規則やモジュール境界が必要になる |
| `development-guidelines.md` | 開発コマンド、命名、コーディング、テスト、Git、レビュー規則 | 反復可能な開発方法が変わる |
| `glossary.md` | 意味の合意が必要なドメイン語とコード上の対応 | 新しい重要語、意味変更、命名衝突がある |
| `development-roadmap.md` | フェーズ、実行順、完了条件、主要依存 | 製品計画やフェーズ境界が変わる |

## `init` での作成基準

標準セットは `product-requirements.md`、`architecture.md`、`development-guidelines.md`、`development-roadmap.md` の4ファイル。次は**必要な永続情報がある場合だけ**作成する:

- `functional-design.md`: 複数の主要フロー、API、永続データ、画面遷移を設計する場合
- `repository-structure.md`: README やフレームワーク既定だけでは配置・境界を判断できない場合
- `glossary.md`: 一般語では表せないドメイン語や、コードとの対応が必要な場合

既存プロジェクトが7文書を採用済みなら維持する。空の見出しや一般論で文書を埋めない。

## 読み込みルーティング（ピンポイント再読用）

細部が必要になったら所有文書の該当節へ直行する。複数領域にまたがる場合も、各文書の関係する節だけ読む。

- ユーザー向けスコープ・受け入れ条件 → product-requirements
- 振る舞い・API・データ → functional-design
- 技術・境界・依存 → architecture
- 配置判断 → repository-structure
- コマンド・テスト・Git → development-guidelines
- 用語 → glossary
- フェーズ・順序 → roadmap

## 更新しない例

次はステアリングやコードコメントへ残し、永続文書へ複製しない:

既存仕様どおりのバグ修正 / 公開契約を変えない内部リファクタリング / テストの追加・整理 / 同じ配置規則内でのファイル追加 / タスクの細かな進捗 / 一時的な調査結果

## 章立て

生成順序は `init-setup.md` の手順 2 を参照（先行ドキュメントの決定事項に後続が従うため、順序を守る）。

- **product-requirements.md** - プロダクト要求定義書
  - プロダクトビジョンと目的
  - ターゲットユーザーと課題・ニーズ
  - 主要な機能の定義
  - 成功の定義
  - ビジネス要件
  - ユーザーストーリー
  - 受け入れ条件
  - 機能要件
  - 非機能要件
- **functional-design.md** - 機能設計書（条件付き）
  - 機能ごとのアーキテクチャ
  - システム構成図
  - データモデル定義(ER図含む)
  - コンポーネント設計
  - ユースケース図、画面遷移図、ワイヤーフレーム
  - API設計(将来的にバックエンドと連携する場合)
  - ドメイン（境界づけられたコンテキスト）分割と、各レイヤー／モジュールの責務（単一責任）・依存方向、ポート（interface）の定義場所・実装場所（`architecture-principles.md` を参照）
- **architecture.md** - 技術仕様書
  - テクノロジースタック
  - 開発ツールと手法
  - 技術的制約と要件
  - パフォーマンス要件
  - 採用したアーキテクチャ選択とその理由（`architecture-decisions.md` の決定を記録）
  - アーキテクチャ原則（単一責任・一方向依存・疎結合・依存性逆転）と、それを担保する技術方針（`architecture-principles.md` を参照）
- **repository-structure.md** - リポジトリ構造定義書（条件付き）
  - フォルダ・ファイル構成（ドメイン駆動 × レイヤードの場合、`src/modules/<domain>/{domain,application,infrastructure,presentation}` + `src/shared/`）
  - ディレクトリの役割
  - ファイル配置ルール（ドメイン分割・ドメイン間の結合ルール含む）
  - 依存方向のルールと、ポート定義層／実装層の配置（依存性逆転の担保。`architecture-principles.md` を参照）
  - 実ファイル一覧ではなく、安定した配置・公開境界の規則を書く
- **development-guidelines.md** - 開発ガイドライン
  - コーディング規約
  - 命名規則
  - スタイリング規約
  - テスト規約
  - Git規約
  - 依存方向・依存性逆転・SDK 型の境界越え禁止など、アーキテクチャ原則を守る運用規約（`architecture-principles.md` を参照）
- **glossary.md** - ユビキタス言語定義（条件付き）
  - ドメイン用語の定義
  - ビジネス用語の定義
  - UI/UX用語の定義
  - 英語・日本語対応表
  - コード上の命名規則
- **development-roadmap.md** - 開発工程
  - フェーズ、実行順、完了条件（個別タスクの進捗は書かない）

## 図表をどこに書くか

設計図・ダイアグラムは独立したフォルダを作らず、関連する上記ファイル内に直接記載する。
配置ルールと記述形式は `diagram-conventions.md` を参照。
