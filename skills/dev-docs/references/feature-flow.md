# 機能追加・修正の手順

`/dev-docs <YYYYMMDD>-<開発タイトル>` で実行する手順。

> Issue 起票から PR・main マージまで自動で回したい場合は `/add-feature` を使う。以下はその土台となる手順。

ステアリングの仕様は `steering-spec.md`、設計原則は `architecture-principles.md` を参照。

## 0. コンテキストの取得（`docs-digest` に委譲）

実装の前提（技術スタック・実行コマンド・Git 規約・命名規則・配置ルール・テスト規約）は、`docs-digest` サブエージェントに取得させる。今回の変更内容をフォーカスとして渡す。**メインで `docs/` の原文を読み込まない。**

## 1. 影響分析（`Explore` に委譲）

既存コードへの影響範囲の洗い出しは、組み込みの `Explore` サブエージェントに委譲する。返させるのは次の3点だけ:

1. 変更が必要なファイルと `file:line`
2. 踏襲すべき既存パターン
3. 再利用できる既存の関数・ユーティリティ

そのうえでメインが判定する:

- 永続的ドキュメント（`docs/`）への影響があるか。**更新するのは承認後も残る製品契約・基本設計が変わる場合だけ**（既存仕様どおりのバグ修正・内部リファクタリング・テスト追加・局所的な実装詳細では更新しない）。
- 更新する場合は所有文書を1つに定め（`permanent-docs-chapters.md` の所有範囲）、どう更新するかを控える（実際の更新は手順 4）。

## 2. ステアリングディレクトリ作成

開発タイトルを決める（引数から。日本語説明なら短い英語ケバブケースに変換）。
SKILL.md「ステアリングディレクトリの作成」に記載の `scripts/new-steering.ps1` を
`-Title <開発タイトル>` で実行する。

## 3. 作業ドキュメント作成と承認（1回だけ）

`.steering/[YYYYMMDD]-[開発タイトル]/` に3ファイルを**一括作成**する（章立てと重複禁止ルールは `steering-spec.md`）:

1. `requirements.md` - 要求内容
2. `design.md` - 設計（永続文書の更新対象もここに明記）
3. `tasklist.md` - タスクリスト

作成後、各ファイルの要点サマリ・永続文書更新の有無・主要タスクを提示し、**1回だけ**承認を得てから実装に進む。全文は貼らない。修正要望があれば直して再提示する。

## 4. 永続的ドキュメント更新（必要な場合のみ）

変更が基本設計に影響する場合、該当する `docs/` 内のドキュメントを更新する。
更新は `doc-writer` に1ファイルずつ委譲する。章立ては `permanent-docs-chapters.md`。

## 5. 実装開始

`tasklist.md` に基づいて実装を進める。`tasklist.md` は細かな作業ごとに編集せず、計画変更時と完了時にまとめて更新する。

## 6. 品質チェック

SKILL.md の「品質チェック（全フロー共通）」に従う。
