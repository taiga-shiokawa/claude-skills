# 作業単位のドキュメント（`.steering/`）の仕様

`/dev-docs` の参照資料。ステアリングディレクトリの命名規則と、その中に置く3ファイルの章立てを定義する。

## ディレクトリ命名規則

```
.steering/[YYYYMMDD]-[開発タイトル]/
```

**例:**

- `.steering/20250103-initial-implementation/`
- `.steering/20250115-add-tag-feature/`
- `.steering/20250120-fix-filter-bug/`

**日付は実行時に取得する。プレースホルダ（`[YYYYMMDD]`）をそのままディレクトリ名にしない。**
作成には SKILL.md「ステアリングディレクトリの作成」に記載の `scripts/new-steering.ps1` を使う
（スキルディレクトリの絶対パスは SKILL.md 側に展開されている）。スクリプトが実行時日付を解決して
ディレクトリを作り、`CREATED<TAB><path>` または `EXISTS<TAB><path>` を返す。

リポジトリの `CLAUDE.md` にこれと異なる命名規則があれば、そちらに従う。

## 3ファイルの章立て

特定の開発作業における「**今回何をするか**」を定義する一時的なステアリングファイル。
作業完了後は参照用として保持するが、新しい作業では新しいディレクトリを作成する。

- **requirements.md** - 今回の作業の要求内容
  - 変更・追加する機能の説明 / ユーザーストーリー / 受け入れ条件 / 制約事項
- **design.md** - 変更内容の設計
  - 実装アプローチ / 変更するコンポーネント / データ構造の変更 / 影響範囲の分析 / 永続文書の更新対象
- **tasklist.md** - タスクリスト
  - 具体的な実装タスク（チェックボックス形式）/ 完了条件

## 3ファイルの規律（重複禁止）

- **3ファイルで文章を使い回さない。** 要求は `requirements.md` にだけ書き、`design.md` からは参照する。設計説明を `tasklist.md` へ転記しない。
- 背景や要求を Issue・PR へも繰り返さない。Issue は要求の短い要約とステアリングへの参照、PR は実装差分と検証結果に限定する。
- **`tasklist.md` は細かな作業ごとに編集しない。** 計画変更時と完了時にまとめて更新する。作業中の細かな進捗は実行時の計画（TodoWrite 等）で管理する。

## 承認の粒度

**3ファイルを一括作成し、実装に入る前の承認1回にまとめる**（`/dev-docs` の feature モード・`/add-feature` 共通）。
ファイル単位の承認は求めない。承認時は全文を貼らず、各ファイルの要点サマリを提示する。
リポジトリの `CLAUDE.md` に異なる規則があればそちらに従う。
