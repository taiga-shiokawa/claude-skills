# 初回セットアップの手順

`/dev-docs init` で実行する手順。`docs/` の永続的ドキュメントと `CLAUDE.md` を整備し、
初回実装用のステアリングまで用意する。既存ファイルを保護しながら、不足分だけを作成する。

各ファイルの所有範囲・章立て・作成基準は `permanent-docs-chapters.md`、ステアリングの仕様は `steering-spec.md`、
図表の書き方は `diagram-conventions.md`、設計原則は `architecture-principles.md` を参照。

## 0. 既存ドキュメントの確認（上書き防止）

セットアップを始める前に、必ず現状を確認する:

- `docs/` に永続的ドキュメントが**すでに存在する場合は、いきなり作成・上書きしない**。既存ファイルを列挙して現状を要約し、「不足ファイルのみ作成（既定）/ 作り直し / 中止」をユーザーに確認してから進める。
- `docs/ideas/initial-requirements.md`（初期要求メモ）が存在しない場合は、先に `/init-idea` で作成することを提案する。ユーザーが不要と判断した場合のみ、ヒアリングしながらセットアップを続行してよい。

## 1. フォルダ作成

```
New-Item -ItemType Directory -Force docs, .steering
```

## 1.5. リポジトリ実態の調査（`Explore` に委譲）

生成する docs は「**何を作るか**（＝初期要求メモ）」と「**どう作るか**（＝このリポジトリの実態）」の両方を反映する。後者を、組み込みの `Explore` サブエージェントに調べさせる。**メインでディレクトリを舐めない。**

返させる内容を明示して依頼する:

- 言語・フレームワーク・主要ライブラリと**バージョン**（マニフェストの実値）
- build / 開発サーバ / lint / 型チェック / テスト / フォーマットの**実コマンド**（`package.json` の `scripts`、`pyproject.toml` 等から。存在しないものは「なし」と明記させる）
- ディレクトリ構成の要約（深さ2〜3）
- 既存の `docs/` `CLAUDE.md` `README.md` の有無
- Lint / フォーマッタ / テストランナーの設定ファイルの有無

空のリポジトリなら「未構成」と返させ、初期要求メモ＋推奨構成（`architecture-principles.md`）から初期構成を提案する。

## 1.7. アーキテクチャ選択の確定（承認はここで1回だけ）

1. 初期要求メモ・既存コード（手順 1.5 の結果）・既存文書から、**確定済みの設計**を抽出する。
2. 未確定で実装や文書構成に影響する選択がある場合だけ `architecture-decisions.md` を読み、関係する質問を最大3問に絞って `AskUserQuestion` で**1回**にまとめて承認を得る（推奨案を先頭に、影響を1文ずつ）。
3. すべて確定済みなら、承認を求めずにそのまま進む。
4. **以降、ファイル単位・章単位の承認は求めない。** 品質は手順 3.5 の横断レビューで担保する。

## 2. 永続的ドキュメント作成（`docs/`）

**標準セットは4ファイル**: `product-requirements.md` / `architecture.md` / `development-guidelines.md` / `development-roadmap.md`。
`functional-design.md` / `repository-structure.md` / `glossary.md` は `permanent-docs-chapters.md` の作成基準を満たす場合だけ加える。内容を持たない文書をファイル数合わせで作らない。

**この順序で逐次生成する**（作成対象のみ。章立ては `permanent-docs-chapters.md`）:

1. `docs/product-requirements.md`
2. `docs/functional-design.md`（条件付き）
3. `docs/architecture.md`
4. `docs/repository-structure.md`（条件付き）
5. `docs/development-guidelines.md`
6. `docs/glossary.md`（条件付き）
7. `docs/development-roadmap.md`

**各ファイルの執筆は `doc-writer` サブエージェントに委譲する。** 起動のたびに次を渡す:

- 生成対象ファイルのパス
- 情報源: `docs/ideas/initial-requirements.md` のパス
- 章立ての定義: `permanent-docs-chapters.md` のパス（原文をメインで読んで渡さない。パスを渡して読ませる）
- 手順 1.5 で得たリポジトリ実態サマリと、手順 1.7 で確定したアーキテクチャ選択
- **既に確定した先行ドキュメントの決定事項**（`doc-writer` が返す「次のファイルへの引き継ぎ事項」をそのまま次に渡す）

**重要:**

- **1ファイルごとの承認は取らない。** まとめて生成し、手順 3.5 の横断レビュー結果と併せて一度だけユーザーに提示する。
- **並列生成しない。** 上の順に逐次実行する。後続ドキュメントは先行の決定事項（技術選定・レイヤー構成・命名規則）に従う必要があり、並列にすると整合性が壊れる。
- `doc-writer` が「矛盾の検知」を返したときだけ、次に進む前にユーザーに提示して解消する。

## 3. CLAUDE.md の作成・更新

CLAUDE.md を作成する（既存なら該当セクションを追記・更新する）。記載する内容は次に**限定**する:

1. **ステアリング規則の要約**: `.steering/[YYYYMMDD]-[開発タイトル]/` に `requirements.md` / `design.md` / `tasklist.md` の3ファイルを作成すること、およびディレクトリ命名規則
2. **プロジェクト固有情報**: 確定した技術スタック、ビルド・テスト・lint の実行コマンド、仮想環境の有効化方法など
3. **プロセスへの参照**: 「開発プロセスの詳細ルール（ドキュメント構成・承認手順・図表規約など）は `/dev-docs` に従う」という1行

**`/dev-docs` の全文や詳細ルールを CLAUDE.md に書き写さないこと。** CLAUDE.md は毎セッション読み込まれるため、詳細ルールのコピーはコンテキストの浪費と規則の乖離を招く。

`doc-writer` に委譲してよい。その場合は「記載内容を上記3項目に限定する」制約を明示的に渡すこと。

## 3.5. ドキュメント横断レビュー（必須）

**生成した docs + `CLAUDE.md` が揃った時点で、`/review-docs` を必ず実行する。**

手順 2 は 1ファイルずつ逐次生成するため、各ファイル単体では整合していても**ドキュメント間の不整合**（技術スタックの食い違い、要求 → 設計のトレーサビリティ欠如、用語の表記ゆれ、配置規則と実構成の乖離）が残りうる。それを検出する手段はここしかないので、スキップしない。

- 生成ファイル一覧・採用したアーキテクチャ選択・`review-docs` の指摘リストを、**まとめて一度**ユーザーに提示する（ここが init 唯一の確認ポイント。手順 1.7 の選択承認を除く）。
- **Critical は実装に入る前に必ず修正する**（誤った設計の上に実装すると手戻りが大きい）。Major はユーザーと相談して要否を判断する。
- 修正は `doc-writer` に該当ファイルを渡して行い、修正後にもう一度 `/review-docs` をかける。

## 4. 初回実装用のステアリングファイル作成

SKILL.md「ステアリングディレクトリの作成」に記載の `scripts/new-steering.ps1` を
`-Title initial-implementation` で実行し、3ファイル（`requirements.md` / `design.md` / `tasklist.md`）を一括作成する。
章立てと重複禁止ルールは `steering-spec.md`。要点サマリを提示して承認を得てから実装に進む。

## 5. 環境セットアップ

リポジトリの実態（手順 1.5 の結果）に従って、依存インストール・仮想環境・環境変数を用意する。
手順は `docs/architecture.md` と `CLAUDE.md` に記録する。

## 6. 実装開始

`.steering/[YYYYMMDD]-initial-implementation/tasklist.md` に基づいて実装を進める。

## 7. 品質チェック

SKILL.md の「品質チェック（全フロー共通）」に従う。
