# アーキテクチャ選択

`/dev-docs` の参照資料。アーキテクチャ文書（`architecture.md`、アーキテクチャを含む `functional-design.md`、境界・依存方向を定める `repository-structure.md`）を新規生成・実質変更し、**既存情報だけでは重要な選択を確定できない場合だけ**参照する。

## 質問の作り方

- 既存コード、ユーザー要求、既存文書ですでに決まっていることは質問しない。
- 実装や文書構造に影響する未確定事項だけを質問する。
- 1問につき2〜3個の排他的な選択肢を示す。
- 現状と要求に最も合う案を先頭に置き、ラベル末尾に `(Recommended)` を付ける。
- 各選択肢の一般的な利点ではなく、**今回のプロジェクトに対する影響を1文**で示す。
- 最大3問を **`AskUserQuestion` ツールで1回**にまとめて聞く。回答後に別の承認ゲートを追加しない。
- ファイル単位・章単位・図表単位の承認は求めない。

## 選択候補

以下をすべて質問するのではなく、今回未確定のものだけを選ぶ。

### 構造スタイル

- **既存構造を維持**: 稼働中のコードがあり、変更理由がない場合に優先する。
- **ドメイン駆動 × レイヤードのモジュラモノリス**（`architecture-principles.md` の推奨構成）: 複数の明確な業務境界と長期的なルールがある場合に向く。
- **機能・ユースケース単位の縦割り**: 業務境界は比較的軽く、機能ごとの変更独立性を高めたい場合に向く。
- **フレームワーク標準または単純レイヤード**: 小規模で、抽象化コストを抑えたい場合に向く。

実際に提示する際は、上記から関係する2〜3案だけを選ぶ。

### 実行・配備構成

ブラウザ・静的配信 / 単一サーバーまたはモノリス / サーバーレス関数を含む構成 / 独立サービス構成。
要求で確定している場合は質問しない。将来候補を現在の構成へ追加しない。

### 状態と永続化の境界

ローカル・ファイルのみ / 単一データベース / 外部サービスをアダプタ越しに利用 / 複数サービスがそれぞれ状態を所有。
認証、監査、同期、オフライン要件などが構造を左右するときだけ質問する。

### 境界と依存方向

フレームワーク既定の境界 / application・domain を内側に置くレイヤード構成 / 公開契約を持つモジュール境界。
構造スタイルの回答から自明なら、別質問にしない。

## DDD・Layered を選んだ場合

次だけをプロジェクト固有の名前へ具体化して `architecture.md` に記録する（チェック観点は `architecture-principles.md`）。

- 境界づけられたコンテキストと各責務
- 各コンテキストの公開契約
- レイヤーの依存方向
- 外部依存を実装するアダプタと、抽象を所有する層
- 具象を組み立てる場所
- 境界違反を検出するテストまたは lint 方針

一般的な DDD 解説や、まだ存在しない将来ドメインの設計は書かない。

## 決定の記録

- 採用案と今回の理由を `architecture.md` に簡潔に書く。
- 他の文書では決定を再説明せず、`architecture.md` を参照する。
- 長期的で代替案との比較が重要な決定だけ ADR へ残す。
- 採用しなかった案を列挙するだけの文書は作らない。
