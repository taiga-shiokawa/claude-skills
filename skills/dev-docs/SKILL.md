# ドキュメント駆動開発プロセス

永続的な仕様を `docs/`、作業単位の仕様を `.steering/` に分けて管理する。このスキルは文書体系の初期化・監査・更新と標準ルールの適用を担当する。Issue 起票から PR・main マージまでの自動実行は `/add-feature` を使う。

引数: `$ARGUMENTS`

## モード別の手順（該当する reference だけを読む）

| 引数 | 何をするか | 読む reference |
| --- | --- | --- |
| **なし** | 本ファイルのルールを以降の作業に適用するのみ。**ファイルの作成・変更は行わない。** `docs/` と `.steering/` の有無を簡潔に報告し、未整備なら `/dev-docs init` を、機能追加なら `/add-feature` を案内する | なし |
| `init` | 初回セットアップを実行 | `references/init-setup.md` |
| `audit` | `review-docs` サブエージェントで `docs/` と `CLAUDE.md` の重複・欠落・矛盾・真の情報源を監査し、指摘リストだけを報告する。**明示的に修正も依頼された場合のみ** `doc-writer` で編集する | なし |
| `update <対象>` | ユーザーが指定した文書、または明示された仕様変更に関係する文書**だけ**を `doc-writer` で更新する | `references/permanent-docs-chapters.md` |
| `<YYYYMMDD>-<開発タイトル>`（例: `20250115-add-tag-feature`） | 機能追加・修正を実行し、そのステアリングディレクトリを作成 | `references/feature-flow.md` |

**該当しないモードの reference を読まないこと。** 本スキルを分割している目的がそれである。
各 reference は必要になった時点で、その中で指示されている他の reference（章立て定義・設計原則など）を追加で読む。

## 真の情報源の優先順位

1. 現在のユーザー要求と明示的な決定
2. `CLAUDE.md` に記載されたプロジェクト固有規則
3. 現行の永続的ドキュメント（`docs/`）
4. `docs/ideas/initial-requirements.md`（初期要求メモ）と過去のステアリング

初期要求メモはプロジェクトの起点であり、**常に最新の仕様とは限らない**。`init`・要求の起点確認・`CLAUDE.md` が真の情報源に指定している場合だけ参照し、現行仕様と矛盾する場合は勝手に統合せず差分を報告する。過去の `.steering/` は、現在の変更と直接関係するものだけ読む。

## プロジェクト構造

- **永続的ドキュメント（`docs/`）** — アプリケーション全体の「何を作るか」「どう作るか」。標準4ファイル＋条件付き3ファイル。所有範囲・更新条件・章立ては `references/permanent-docs-chapters.md`
- **作業単位のドキュメント（`.steering/[YYYYMMDD]-[開発タイトル]/`）** — 特定の作業の「今回何をするか」。3ファイル。仕様は `references/steering-spec.md`

## ステアリングディレクトリの作成

**日付は実行時に取得する。プレースホルダをそのままディレクトリ名にしない。** 同梱スクリプトを使う:

```
${CLAUDE_SKILL_DIR}/scripts/new-steering.ps1 -Title <開発タイトル>
```

`CREATED<TAB><path>` か `EXISTS<TAB><path>` を返す。`EXISTS` の場合は上書きせず、
新規作業なら別のタイトルにする。リポジトリの `CLAUDE.md` に異なる命名規則があればそちらに従う。

## サブエージェント運用方針（全コマンド共通）

ドキュメント駆動開発では、実装に入る前に大量の原文（`docs/`、仕様、既存コード）を読む必要がある。これを**すべてメインコンテキストで読むと、一番コンテキストが必要な実装フェーズで枯渇する**。したがって次を全コマンド共通のルールとする。

### 委譲するもの（隔離コンテキストのサブエージェントに肩代わりさせる）

原文が重く、**メインには結論だけあればよい**作業:

- 永続的ドキュメント（`docs/`）・`CLAUDE.md` の読み込み → `docs-digest`（実装前提ダイジェストを返す）
- ドキュメントのレビュー・監査 → `review-docs`（指摘リストだけを返す）
- 永続的ドキュメントの生成・更新 → `doc-writer`（1ファイルずつ。書いたパスと要約だけを返す）
- 外部仕様（FieldSpec OS MCP）の取得 → `fsos-spec-fetcher`（キャッシュに逃がし、索引だけを返す）
- コードベースの影響範囲調査・既存パターンの探索 → 組み込みの `Explore`
- アプリの動作検証（サーバログ・ブラウザ操作など出力が冗長なもの）→ 組み込みの `general-purpose`
- テストの作成・実行 → プロジェクトに `test-writer` エージェントがあればそれ
- 実装差分のレビュー → プロジェクトに `code-reviewer` エージェントがあればそれ

### メインに残すもの（委譲しない）

- **ユーザーとの対話・承認ゲート** — サブエージェントはユーザーに質問できない
- **実装本体** — 文脈の連続性が必要で、細切れに委譲すると整合性が崩れる
- **git / gh などの不可逆操作**（commit / push / PR 作成 / マージ / Issue 起票）— 判断を伴い、取り返しがつかない

### 委譲先の使い分け

| 種類 | 使うもの | 判断基準 |
| --- | --- | --- |
| 決まった形式で返す契約が必要 | 専用エージェント（`~/.claude/agents/`） | 出力を後続ステップが機械的に使う |
| 汎用的な探索・調査 | 組み込み `Explore` | 「どこにあるか」を知りたいだけ |
| 実行と検証 | 組み込み `general-purpose` | コマンド実行が必要で出力が冗長 |

### 守ること

- **委譲した対象の原文を、メインで読み直さない。** 読み直したら委譲の意味が消える。必要になったら、返ってきた出典ポインタ（`ファイル > セクション`）を頼りに該当箇所だけを `Read` する。
- サブエージェントには**返してほしい形式を明示**する。曖昧に投げると原文が返ってきてコンテキストを食う。
- 承認ゲートは必ずメインで取る。サブエージェントに承認を代行させない。

## 承認の方針（全コマンド共通）

- 選択式の承認は、**未確定のアーキテクチャ判断を文書へ確定するときだけ**求める。質問は最大3問に絞り、**1回**にまとめる（質問の作り方は `references/architecture-decisions.md`）。
- 文書作成そのもの、非アーキテクチャ文書、ファイル単位・章単位の確認では承認を求めない。品質は `review-docs` による横断レビューで担保する。
- 選択済みの内容をそのまま文書化する場合、表現や章立てだけを変える場合は承認を求めない。
- ステアリング3ファイルは一括作成し、実装前の承認1回にまとめる（`references/steering-spec.md`）。

## 品質チェック（全フロー共通）

- Lint・型チェック・関連テストを実施する。実際のコマンドは `CLAUDE.md` / `docs/architecture.md` / マニフェスト（`package.json`・`pyproject.toml` 等）から判断する。設定が無いものはスキップし、その旨を報告に明記する（勝手に新ツールを導入しない）。
- `references/architecture-principles.md`（単一責任・一方向依存・疎結合・依存性逆転）に照らし、ドキュメントとコードが原則を満たしているか確認する。

## ドキュメント管理の原則

### 永続的ドキュメント（`docs/`）

- アプリケーションの基本設計を記述し、大きな設計変更時のみ更新する（プロジェクト全体の「北極星」）
- **既存仕様どおりのバグ修正・内部リファクタリング・テスト追加・局所的な実装詳細では更新しない**

### 作業単位のドキュメント（`.steering/`）

- 特定の作業・変更に特化し、作業ごとに新しいディレクトリを作成する
- 作業完了後は履歴として保持し、変更の意図と経緯を記録する

### 重複の禁止

- 同じ説明を複数文書へ複製しない。**所有文書に1回だけ記述し、他文書から参照する**
- 内容を持たない文書をファイル数合わせで作らない
- 永続文書・ステアリング・Issue・PR・完了報告で同じ文章を重複させない

## 注意事項

- **`docs/` の原文をメインコンテキストに読み込まない**（「サブエージェント運用方針」参照）
- 既存文書やユーザーの変更を無断で上書き・作り直ししない
- 永続的ドキュメントと作業単位のドキュメントを混同しない
- コード変更後は必ずリント・型チェックを実施する
- セキュリティを考慮したコーディング（XSS対策、入力バリデーションなど）
- 図表は関係を文章より明確にできる場合だけ、所有文書内に Mermaid で記載する（詳細は `references/diagram-conventions.md`）
- アーキテクチャは `references/architecture-principles.md` の4原則を満たすこと

## Environment / Running

環境固有の前提（言語バージョン、依存関係、仮想環境の有効化）とアプリの起動方法は、各リポジトリの `CLAUDE.md` / `docs/architecture.md` / `README.md` を参照すること。仮想環境がある場合は、コマンド実行前に必ず有効化する。
