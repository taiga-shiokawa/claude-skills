> **位置づけ**: このコマンドはドキュメント駆動開発の **起点** を作る。ここで生成する `docs/ideas/initial-requirements.md` は、後続の `/dev-docs` が「真の情報源」として参照するファイルである。
> **後続フロー**: 作成後は `/dev-docs init` → 必要に応じ `/review-docs` → `/add-feature <機能>` の順で進む。

# アイデア初期要求メモの作成

ユーザーのアイデアを **対話でヒアリング**し、「タイトル」「背景」「やりたいこと」の3セクションを埋めた初期要求メモを `docs/ideas/initial-requirements.md` として作成する。

引数（アイデアの概要・任意）: `$ARGUMENTS`

## 出力仕様

- 出力先: `docs/ideas/initial-requirements.md`（1ファイルのみ）
- セクションは必ず次の3つ。順序も固定する。
  1. **タイトル** — アイデアの名前 / 一言サマリ
  2. **背景** — なぜやりたいか（動機）・現状の課題・前提・コンテキスト
  3. **やりたいこと** — 実現したいこと・想定する成果物・スコープ（すでに確定している技術スタックがあればここに併記）

## 手順

### 1. 出力先フォルダの準備

`docs/` は存在する前提だが、`docs/ideas/` がなければ作成する。

```bash
mkdir -p docs/ideas
```

### 2. 既存ファイルの確認（上書き防止）

`docs/ideas/initial-requirements.md` がすでに存在する場合は、**いきなり上書きしない**。
中身を読んで現状を要約し、「追記・改訂するか / 新しい内容で作り直すか / 中止するか」をユーザーに確認してから進める。

### 3. アイデアのヒアリング（対話）

3セクションを埋めるために必要な情報を、ユーザーに質問して集める。

- `$ARGUMENTS` にアイデアの概要が渡されていれば、それを下書きの種として使い、各セクションのドラフトを起こす。**不足している部分だけ**を質問で補う。
- 引数がなければ、3セクションそれぞれについてユーザーにヒアリングする。
- 質問は**自由記述で自然に問いかける**こと（アイデアの中身は選択肢化しにくいため、AskUserQuestion ではなく通常の会話で尋ねる）。明確な二択・三択がある場合に限り AskUserQuestion を使ってよい。
- ヒアリングは軽量に保つ。**一度に詰問しすぎない**（1〜2問ずつ、多くても3問程度）。すでに会話や引数から判明している内容を聞き返さない。

各セクションで引き出したい観点の目安:

- **タイトル**: このアイデアを一言で言うと？ 仮称でよい。
- **背景**: なぜ今これをやりたい？ 解決したい課題や困りごとは？ 既存の手段では何が足りない？ 誰のためか？
- **やりたいこと**: 最終的に何が出来上がっていれば成功？ 主要な機能・成果物は？ 今回のスコープ（やること / やらないこと）は？ 使うと決めている技術があれば？

### 4. ドラフトの提示と確認

集めた情報で3セクションを埋めたドラフトを作成し、ユーザーに提示して確認・修正を受ける。曖昧なままの箇所は「TBD」と明記し、放置しない。

### 5. ファイル書き出し

確認が取れたら、下記テンプレートに沿って `docs/ideas/initial-requirements.md` を書き出す。冒頭の日付は今日の日付（`currentDate`）を使う。

```markdown
# 初期要求メモ

> プロジェクトの起点となる要求メモ。`/dev-docs` が「真の情報源」として参照する。
> 作成日: YYYY-MM-DD

## タイトル

<アイデアの名前・一言サマリ>

## 背景

<なぜやりたいか・現状の課題・前提・コンテキスト>

## やりたいこと

<実現したいこと・想定する成果物・スコープ（確定済みの技術スタックがあれば併記）>
```

### 6. 次のステップを案内

作成完了後、ユーザーに `docs/ideas/initial-requirements.md` のパスを伝え、「内容を確定できたら `/dev-docs init` で永続的ドキュメントの整備に進める」と案内する。

## 原則

- セクションは3つ（タイトル / 背景 / やりたいこと）に限定し、勝手に増やさない。
- このファイルは設計を確定する場ではなく、**アイデアの出発点**を素早く形にする場。完璧を求めず、空欄は「TBD」で残してよい。
- ユーザーの言葉・意図を尊重し、過剰な脚色や勝手な前提追加をしない。
